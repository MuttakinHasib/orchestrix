# Rule: Commit conventions

Rules for git commit message titles in this repository. These conventions override any global or skill-provided commit style (e.g. Conventional Commits) — when they conflict, this file wins.

## 1. The "If merged, this commit will" test

Every commit title must complete the sentence:

> If merged, this commit will **\<commit title\>**.

If the resulting sentence reads as grammatical English and makes sense, the title passes. If it does not, the title is not according to our conventions and must be rewritten.

This forces titles to:

- Use imperative mood (e.g. "Add", "Fix", "Hide", "Remove", "Refactor", "Move", "Restore").
- Describe the effect of merging the commit, not the author's past action.
- Skip prefixes like `fix:`, `feat:`, `chore:`, etc. — those break the sentence.

### Examples

| Title | Sentence | Verdict |
| --- | --- | --- |
| `Hide cancelled executions from the board unless the failed filter is on` | "If merged, this commit will Hide cancelled executions from the board unless the failed filter is on." | Pass |
| `fix: hide cancelled executions` | "If merged, this commit will fix: hide cancelled executions." | Fail — `fix:` breaks the sentence |
| `Hidden executions on the board` | "If merged, this commit will Hidden executions on the board." | Fail — past participle, not imperative |
| `Fixing the board filter bug` | "If merged, this commit will Fixing the board filter bug." | Fail — gerund, not imperative |
| `Board filter fix` | "If merged, this commit will Board filter fix." | Fail — noun phrase, not a verb |
| `Move IssueStatus block from the issues module into packages/ui` | "If merged, this commit will Move IssueStatus block from the issues module into packages/ui." | Pass |

## 2. Capitalization

The first character of the commit title must be a capital letter — always.

Subsequent characters follow normal English casing rules — they may be lowercase or uppercase depending on the words used (proper nouns, acronyms, file/symbol names, etc. stay as written).

### Examples

| Title | First char | Verdict |
| --- | --- | --- |
| `Hide cancelled executions from the board` | `H` | Pass |
| `Restore selected-row accent on the executions table` | `R` | Pass |
| `hide cancelled executions from the board` | `h` | Fail — first character not capitalized |
| `Add useExecutionFilters hook to core` | `A` | Pass — `useExecutionFilters` keeps its camelCase casing because it is a symbol name |

## 3. Multi-line commits (rare, opt-in only)

Single-line commit titles are the default and the strong preference for this repository. Multi-line commit messages exist but are used sparingly — significantly less often than single-line commits.

**Always generate a single-line commit title unless the user explicitly asks for a multi-line commit message.** Do not auto-promote a commit to multi-line based on your own judgement (e.g. "this touches multiple files" or "these changes feel unrelated"). Wait for the user to ask.

When the user does ask for a multi-line commit — for example because the commit genuinely entails multiple unrelated tasks — follow this format:

1. Line 1: a single-line title that still passes the "If merged, this commit will" test and starts with a capital character (rules 1 and 2 still apply).
2. Blank line.
3. Body opens with the literal phrase: `This commit entails the following changes`
4. Body continues with an unordered list (`-` bullets) where each item describes one change.

### Example

```
Rework the workflows module

This commit entails the following changes
- Hide cancelled executions from the board unless the failed filter is on
- Add commit-conventions rule under docs/rules/
```

## 4. No attribution trailers

Never append a `Co-Authored-By:` trailer (or any other "generated by …" attribution) to commit messages in this repository. Commit messages should be only the title (and, when explicitly requested, the multi-line body from rule 3) — nothing else.

This applies to every commit, regardless of who or what produced the change.

## 5. How to check before committing

Before proposing or running a commit:

1. Read the title aloud after `If merged, this commit will`.
2. Verify the first character is uppercase.
3. Confirm the commit is single-line unless the user explicitly asked for a multi-line message.
4. If any check fails, rewrite the message and re-check.
